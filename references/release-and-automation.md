# Releasing and automation

Read this when cutting a release, and whenever a manual step is about to be repeated. Both are recurring activities, independent of the ten delivery phases.

## Releasing

Use the ecosystem's standard release mechanism, never a hand-typed sequence:

| Ecosystem | Release mechanism |
| --- | --- |
| Maven | **`maven-release-plugin`** — `release:prepare` (version, tag, next snapshot) then `release:perform` |
| Gradle | A release plugin, or `gradle` tasks driven by one committed script |
| npm | `npm version` + `npm publish` from CI, with a committed lockfile |
| Cargo | `cargo release` |
| Go | An annotated tag, since the tag *is* the version |
| Container images | Tagged with the same version as the artifact, never only `latest` |

Rules:

- The release runs from a **clean tree on a green mainline**, with every gate passed. No release from a branch with unmerged work, and no release to "fix it afterwards".
- `CHANGELOG.md`: the *Unreleased* section becomes a version heading with a date, curated for humans, before the tag is created.
- The **SemVer level follows what changed**, not how big the diff felt. A breaking change is a major even if it is one line — the compatibility gate (`oasdiff`, japicmp, revapi) is what decides, not an opinion.
- **SBOM** generated by the build and attached to the release.
- Versions are owned by the release tool. Never hand-edit a version in a file it manages.
- Release automation that requires squashed commits (`semantic-release` and the like) is **not** a default: propose it only if the user asks for it and explicitly accepts giving up the merge-commit history. `git-cliff` drafting a changelog from Conventional Commits gives the same benefit without that trade.
- Everything the tool does not do — publishing docs, pushing an image, notifying, smoke-testing the artifact — is a **script in `scripts/`**, run by CI and runnable locally.
- A release that had to be babysat is a defect: the next ticket automates the part that needed hands.

### Before tagging

A short pre-release check, run every time rather than remembered:

1. Mainline green, all gates including the slow stages.
2. Changelog section complete, with a migration note for every breaking change.
3. Version level matches what the compatibility gate reports.
4. Documentation and diagrams reflect what is being released.
5. No `-SNAPSHOT`, no `TODO`, no debug flag in what ships.
6. The artifact has been started once from a clean environment — a release nobody ran is a hypothesis.

## Automation and scripts

**Anything done by hand a second time becomes a committed script.** Otherwise the knowledge lives in a session that ends.

- Prefer a **tool** over a script, a **script** over a manual step, and never the same manual step twice.
- `scripts/` at the project root, one purpose per script, named after the task, listed in `docs/technical/development.md`.
- **POSIX shell**, portable between the developer's host and Linux, so the same script later runs unchanged inside a Podman container or in CI. Avoid what differs across platforms: `sed -i`, `readlink -f`, `date` flags, GNU-only `find` options, `echo -e`. When a portable form is awkward, prefer a small script *inside a container image* over a host-specific one.
- `set -eu`, and `-o pipefail` only in a script that declares `#!/usr/bin/env bash`: dash — `/bin/sh` on Debian and Ubuntu — does not implement it, and `shellcheck` fails the mismatch as SC3040. Check prerequisites up front with a message that says what is missing and how to get it; be idempotent where the task allows.
- No secrets in a script and none in its output. Read them from the environment or the platform's secret store.
- `shellcheck` runs as a build gate — scripts are code and get the same treatment.
- **CI calls the same scripts**, so a developer can reproduce a CI failure locally. A long list of inline CI steps is a manual process with extra hiding places.

### What is usually worth a script

Not an obligation — a list of the steps that most often get repeated by hand:

| Script | Replaces |
| --- | --- |
| `scripts/build.sh` | The full local build with every gate, one command |
| `scripts/test-integration.sh` | Container-backed suites with their environment set up correctly |
| `scripts/screenshots.sh` | Regenerating documentation screenshots |
| `scripts/release.sh` | The release tool plus whatever it does not cover |
| `scripts/dev-env.sh` | Bringing up the local dependencies (database, broker) via Podman |
| `scripts/check-docs.sh` | `markdownlint` and `lychee` over the docs |

Each of these is also what CI runs, so local and CI behaviour cannot drift.
